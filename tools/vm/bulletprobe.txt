== PFM_NUMBERING/PFN_BULLET on paragraphs 1 and 2 ==
  para 0, still plain    numbering 0      startIndent 0      offset 0      rightIndent 0      align 1   mask 8001003F
  para 1, bulleted       numbering 1      startIndent 0      offset 0      rightIndent 0      align 1   mask 8001003F
  para 2, bulleted       numbering 1      startIndent 0      offset 0      rightIndent 0      align 1   mask 8001003F

  Same startIndent and offset before and after means the
  control does NOT move the text for a bullet, and WordPad's
  menu item must be sending the indents itself. Different means
  the control owns the geometry and it is these numbers.

== where the characters actually land ==
  para 0 first char      index 0    x 1      y 0      
  para 1 first char      index 17   x 12     y 16     
  para 2 first char      index 34   x 12     y 32     
  para 2 wraps at index 92: x 1 y 48 (first line x 12 y 32)

  A wrapped line starting at the same x as the first line means
  the bullet hangs outside the text block. A smaller x means it
  does not.

== dxStartIndent 0, dxOffset 720 -- does that draw WordPad's? ==
  para 2, indents set    numbering 1      startIndent 0      offset 720    rightIndent 0      align 1   mask 8001003F
  para 2 first char      index 34   x 49     y 32     
  wraps at index 86: x 49 (first line x 49)

  First line unmoved and the wrapped line pushed out is the
  mapping confirmed: dxStartIndent is the first line, dxOffset is
  the rest relative to it. Both moving, or the wrong one moving,
  means the dialog's two numbers map the other way about.

== the other combination, for comparison ==

  dxStartIndent 720, dxOffset -720
    para 2 first char   x 60
    wraps at            x 1  (first line x 60)

So `dxStartIndent 0, dxOffset 720` is the pair that draws WordPad's
geometry and the other one does not. The dialog's two numbers mean
`Left = dxOffset` and `First line = dxStartIndent - dxOffset`.
